# Full-model extraction into the six existing prototypes

Read-only source audit. No code edits, test execution, model calls, or production integration. Scope: the six `research/prototypes/*/index.ts` files read for this assignment.

## Finding

A source-reading LLM can propose most of the semantic annotations these prototypes currently receive as fixture data. None of these APIs currently performs that extraction. A bounded JSON decoder and six small, explicit mapping functions would be required; a plugin framework, database, or new mathematical engine would not be required for the experiment.

The important boundary is between **proposed interpretation** and **caller-owned evidence/state**. The extractor can identify an attribution, suggest an occasion boundary, or describe uncertainty. It cannot establish that a source is currently eligible, that its revision exists, that an identity was reviewed, that the supplied population is complete, or that a remembered aid remains applicable merely by emitting those values.

## Material traps for the rerun

1. **JSON shape safety is not already comprehensive.** Several functions assume TypeScript inputs and dereference nested arrays/objects or `.length` before exhaustively checking runtime types (for example relations lines 65–89, operations lines 42–69, experiences lines 37–53, transformations lines 28–38). Calling them directly on parsed model JSON risks exceptions or invalid values being treated as accepted data. A small bounded runtime decoder is necessary. This is adapter work, not a reason to add a general schema framework.

2. **Unknown, empty, absent, false, and unrestricted have different meanings.** A view with missing selected scope/time is unresolved (01 lines 38–45). An empty finite domain is a conflict, not uncertainty (02 line 41). Interval `null` means unbounded, whereas `"unknown"` means unresolved (02 lines 67–69, 101–112). `Report.subjects: null` is unknown; `[]` gives no positive subject matches (03 lines 157–164). A preference Boolean has no unknown variant, so missing evidence requires omission of that preference slot, not `false` (04 lines 54, 181–187). In transformations, `absent` is a positive representation choice; `unknown` prevents a passed equality claim (06 lines 67–72). The extraction prompt and decoder must preserve each API's actual distinction.

3. **Completeness metadata is scoped.** Supplied-population coverage is not universal knowledge completeness. In `jointOccasions`, `coverage.complete` can coexist with `participation-unknown` or unavailable-source entries (05 lines 82–100). A reader must inspect unresolved results, not turn a complete scan into evidence of absence.

4. **Revisions do not authenticate an interpretation.** All six can accept references to current evidence while the extracted claim, attribution, interval, alignment, or interpretation is wrong. Most verify source-state eligibility rather than textual entailment. Even prototype 06 only checks textual quote presence. The evaluation therefore needs a separate extraction-fidelity score before evaluating computation and final answer quality.

5. **A generic rich response would silently overstate present capabilities.** Prototype 04 accepts one recipe. Prototype 03 has fixed paths and one equation. Prototype 06 checks five declared fields, not arbitrary semantic equivalence. A full LLM can extract wider knowledge than these APIs can use; unsupported information must remain out of their outputs or explicitly marked as outside the selected mechanism.

6. **No automatic positive explanation facility exists across all six.** Compatibility can return a conflict with only `assignmentsExamined`; scheduling can return a correct option with `reasons: []` (02 lines 5–7, 57; 04 lines 139–143). The next reader should not be asked to manufacture a proof from that receipt. A plain faithful rendering, or a separately implemented deterministic witness/explanation adapter, should be compared explicitly.

## Minimal recommendation

Use one fresh, bounded extraction call per selected proposal and source bundle. Ask for the narrow candidate payload that the existing operation needs, plus source ID/quote evidence and explicit unresolved items. Keep operation limits, query, actual bytes, revision/state snapshot and reviewer decisions outside the model's response schema. Decode and map once; either supply valid, grounded candidate data or return an explicit extraction failure/unknown result. Preserve the raw response and all rejected/missing fields for scoring.

For this experiment, store model-proposed semantic decisions as such. Where the API expects reviewed identities/alignment/applicability, compare them with independently prepared labels rather than pretending a mechanical parser performed that review. A later production design could decide how those candidates are accepted; this audit does not propose that policy.

This permits a clean diagnostic separation: **Did the model extract the right facts and uncertainty? Did the existing operation produce its defined result on those inputs? Did the final consumer use that result faithfully?** It also permits an equal-call comparison against a plain-language analysis call without the structured operation, so a second model call does not get mistaken for evidence that the mathematical layer itself caused the gain.
