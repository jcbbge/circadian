# Six optional additions: proposed integration boundaries

Circadian supplies the memory and lifecycle. Each addition performs a bounded operation over explicitly selected material. These are proposed consumer boundaries for the existing research functions, not installed hooks, config keys or a selected plugin framework. The [results](RESULTS.md) give a separate evidence-based disposition for each proposal; this document does not authorize deployment.

## Smallest useful shape

| Addition | Input → output | Proposed activation and Circadian fit | Boundary that still needs evidence |
| --- | --- | --- | --- |
| **01 — Coordinated views** | Source-backed claims with qualifications, current source revisions/eligibility, selector and budget → compact view, references and explicit coverage; expansion returns original text. | A selected recall/render consumer requests a view at the needed detail. The existing `makeView` and `expand` functions remain small, independent operations. | This study kept full sources in every arm. It establishes no context savings, automatic relevance selection or reliable expansion policy. Test those separately before promising a smaller useful wake payload. |
| **02 — Contextual compatibility** | Explicit contextual accounts/alignment or finite domains and constraints → compatibility, conflict, separation or uncertainty. | An agent asks whether particular accounts can coexist or a selected group of requirements can jointly hold. `compareContexts` and `checkJoint` attach a report to the selected evidence. | The procedure can check its supplied representation; it cannot certify that a model represented the real context correctly. Missing values for declared dimensions remain unknown; a dimension absent from the supplied representation cannot be detected. Project origin is not semantic applicability. |
| **03 — Typed relations** | Source-backed reports, distinct speaker/subject/place roles, reviewed identities and allowed joins → attributed results and composition evidence. | A targeted recall question asks who said something, whom it concerned and where it happened. `composeReports` supplies the bounded relation report. | Annotation fidelity and identity resolution remain separate problems. A statement about someone must not become their own statement; a recording location must not become an event location. Repeated reports do not automatically become a permanent trait. |
| **04 — Reusable operations** | A known recipe, supplied/bound inputs, current source state and explicit applicability → tentative result, remaining inputs or a reason to decline. | During a relevant task, `instantiate` reuses a small known operation. Retiring an aid does not delete the experience from which it came. | The implementation and this study use planning operations. They do not establish autonomous invention, learning or decay of personal mnemonics, or broad cross-domain recipe reuse. A source-valid aid can still be irrelevant or unhelpful now. |
| **05 — Joint experiences** | Occasions, participation and separately attributed interpretations/revisits with source state → bounded occasion recall or joint-incidence results. | Recall a shared event and later readings of it through `recallOccasion` or `jointOccasions`, alongside committed episodes. | Mention, attendance and interpretation authorship must stay distinct. Selected-seed traversal is not discovery of every relevant reflection. Preserve differing accounts and uncertainty without imposing one final meaning. |
| **06 — Checked transformations** | Original and candidate presentations, designated fields, source revisions, assumptions and a named check mode → per-property pass/fail/not-checked with an input binding; an optional `makeReceipt` call creates a historical receipt. | `checkPresentation` accompanies a proposed rewrite or rendering change before any optional consumer accepts it. | Equal annotations do not prove equivalent arbitrary prose. Free prose remains semantically unassessed by the deterministic checker; unavailable originals prevent a preservation claim. Historical receipts cannot certify changed inputs. |

These boundaries are grounded in the inspected [prototype APIs](../../prototypes/README.md) and [Circadian source map](../../refinements/SOURCE-MAP.md). They are intentionally narrower than the broader conceptual dossiers. The practical operations are restriction/expansion, contextual compatibility, typed composition, specialization, joint incidence and explicit preservation checks. No higher-category engine is needed to execute the selected prototypes.

## Shared contract for a future adapter

1. **Explicit use.** A configured consumer requests one operation. Each addition can be disabled independently. Disabled use must perform no supplemental selection, inference, storage mutation or output change. Enabling one must not require the other five.
2. **Read before derive.** Resolve current source eligibility, availability and revision at use time. Supplied annotations and model choices remain fallible evidence. Missing or unsupported inputs produce a visible bounded limitation; the consumer retains access to ordinary Circadian recall.
3. **Small returned objects.** Return the result with its source references, assumptions, omitted coverage and unknowns. Do not make an operation's output a second authoritative memory or silently turn it into a directive.
4. **No mandatory background work.** The six tested core operations do not need model inference. A future annotation provider can be an optional separate dependency. This run gives no reason to put a classifier on every startup, every memory or every interaction.
5. **Persistence earns its place.** The first consumer can operate on ephemeral derived inputs. If persistent annotations later become useful, they need explicit revision invalidation and forgetting/erasure behavior before live use. Existing deletion commands do not automatically cover new sidecars or paraphrases.
6. **A consumer must demonstrate benefit.** A correct operation is not enough. Its added context, interpretation burden, selection work and calls must be measured against the simplest competent consumer of the same evidence. These prototypes must also prove ordinary disabled behavior and source invalidation at their actual integration boundary.

## What this experiment can decide

The paired comparison isolates supplying an operation result when a reader already has full source evidence and the same supplied annotations. Jev then selects one bounded annotation variant in a separate condition; its uncertainty fallback also removes annotations and the operation. This is not a measurement of automatic capture or an untouched end-to-end default Circadian pipeline.

A positive case can nominate a consumer for confirmation. A tie gives no demonstrated added benefit on that case. A regression identifies a concrete consumer/representation question. With four cases per proposal and one observation per condition, none of these results establishes a universal verdict about the underlying mathematical idea. Output-contract failures must remain visible rather than being mistaken for isolated evidence about memory reasoning.

The assignment ends with the frozen run, blinded review, accounting and six-proposal dispositions. A new experiment or production adapter requires a separately specified scope; neither is automatically started here.
