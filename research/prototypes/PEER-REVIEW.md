One verified behaviour that creates a false-conflict trap. `compareContexts` reads only the dimensions listed in `group.dimensions` (lines 161–162). **05 — Experiences.** Inspected `jointOccasions`, `checkRevisit` and `recallOccasion`. Incidence is correct: mention never implies absence (H03), unresolved participants give participation-unknown (H14), sub-group queries do not create pairwise events (H12), and simultaneous presence requires interval overlap or an explicit co-presence group (H13). The boundary check is exactly occasion ID plus local question ID, author excluded (H07, H16). The incidence comparator is an alias and the demonstration says so plainly.

One verified defect in `recallOccasion`. Traversal seeds only from interpretations with `entry: true` (line 125), and only candidates-type targets are listed as unresolved (line 126). An eligible interpretation whose resolved occasion is the queried ID, with `entry: false` and no incoming checked link, is neither shown nor reported. Counterexample: the H05 population with `revisits: []`. Expected under the refinement, which promises partial coverage and unresolved references rather than silence: accounts `[I1]` plus an unresolved entry for I2, or accounts `[I1, I2]`. Actual: accounts `[I1]`, `unresolved: []`, `coverage.complete: true`. The test asserts this actual value, so H05's deterministic claim that the link "reaches" I2 is partly by construction: the implementation hides I2 with a flag, then the link restores it. The anchorless-retrieval benefit is a claim about lexical retrieval, which this prototype does not model. Smallest correction: seed the queue from every eligible interpretation whose resolved occasion equals the ID, keep revisits as relation edges that order and connect accounts, and restate H05 as "the checked link connects I1 to I2 and rejects mismatched boundaries." If `entry` is kept for ordering, any non-entry interpretation not reached must appear in `unresolved` with reason `unlinked`.

Nothing else material. The `fitOutput` fixpoint loop is a reasonable way to charge the output size against itself.

**06 — Transformations.** Inspected `equalField`, `checkPresentation`, `makeReceipt`, `verifyApplicability`, `historicalReceipt` and the K14 helpers. The corrected three-state rule is implemented: unknown on either side is notChecked, explicit absence against a known value fails (lines 67–70, K04, K07). Prose preservation is always notChecked, and only fixed mode recomputes the exact template (lines 101–104). K06, K13 and K15 show misleading, lossy and faithful free prose all receiving the same field results with prose unassessed, which is the boundary the parent asked for. The binding covers eight components and K10 mutates each separately. A receipt holds digests and property names only, is recomputed internally rather than accepted from the caller, and `verifyApplicability` returns unavailable before comparing digests when inputs or sources are gone (K11, K18). K14 is ordinary property testing of a field-preserving renderer, and the coverage note says so.

Is binding meaningful beyond ordinary validation? Modestly, and the demonstration states the honest conclusion: field equality finds the modality change, binding separately finds the edited candidate. The receipt's only distinct benefit is historical display when inputs are unavailable, which K18 demonstrates and which is suppressible by policy.

One improvement, not a defect. In free mode a reader sees `differences: []` next to changed prose (K06, K13). A byte-inequality property such as `prose-bytes: changed` is not semantic stripping and would stop a blank differences list from reading as reassurance. The parent's earlier rejection concerned extracting fields from prose; a plain inequality of the two byte strings is a different thing.
